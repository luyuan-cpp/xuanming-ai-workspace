# 位图（Bit）存储规范与策划删表 ID 红线（跨仓通用）

> 对应总仓入口 [AGENTS.md](../../AGENTS.md)。适用于所有服务端与客户端仓的存档设计、配表维护与热更逻辑。

## 1. 适用边界：优先用 bit 存储纯布尔状态

- **优先使用 bit（位图）的场景**：玩家针对配置表稳定 ID 的纯布尔状态（`0 / 1`：任务完成、成就解锁、一次性奖励领取、引导步骤完成等）优先用紧凑位图存储（proto 落盘统一为 `bytes`，第 `i` 位落第 `i / 8` 字节的第 `i % 8` 位，低位在前、末尾全 `0` 字节不写）。
- **禁止直接用配置表 ID 当 bit 下标**：配置表 ID 常稀疏或大号起编，必须通过导表器 `(cfg_bit_index) = true` 维护的 `ID -> 紧凑 bit_index` 映射转换。
- **不适合塞进永久单调位图的场景**：① 需要携带进度计数、时间戳等额外字段的状态；② 高频轮换/周期重置的限时运营活动（应按 `activity_id` / 期次独立存档，过期整条清理）；③ 声明了 `(cfg_multi) = true` 的可重复主键表。

## 2. 领取状态归属

- 每个业务系统（任务、成就、每日登录等）各自持有自己的领取状态位图，位序来自**该业务系统自己的表**，**而不是**公共 `Reward` 表。
- `Reward` 表 ID 只是纯数据引用（“发放什么物品/货币”），不作持久化主键；修改任务的奖励引用 ID 不影响玩家已领取状态。

## 3. 删表 ID 机制与三大风险（程序与策划共同遵守）

位序映射的唯一权威源位于权威配表仓 `tools/data_table_exporter/state/mapping/table_index_mapping/<表名小写>_mapping.json`：

1. **删除表行本身安全（空位永久保留不回收）**：导表器永久保留已删 ID 的 bit 位占位并打 warning，新 ID 只从 `max(已分配) + 1` 追加，绝不复用空位。
2. **最致命的坑：「删了又复填旧 ID」或「手改/重建位序映射文件」**：
   - 删掉旧 ID 后再复填给新业务项，老玩家的历史 `1` 位会直接串味为新项“已完成/已领奖”；
   - 删除、手改或重建映射文件会导致整表位序重排，全服存档静默损坏。
3. **热更与灰度 / 混跑三类坑**：
   - **统计口径坑**：不能直接拿原始位图 popcount / `cardinality()` 当作“当前有效完成总数”，必须按当前配置表有效 ID 集合过滤统计；
   - **查表为空容错**：读档或运行时按 ID 查表返回空时必须安全跳过、自动清理或保底处理，不得崩服/阻塞登录；
   - **灰度/滚服高位 bit 透传**：新版本写入的高位未知 bit 被旧版本读盘时，必须**原样保留完整字节数组并在存盘时原样写回**，严禁截断丢弃。

## 4. 策划与程序红线清单

- **策划红线**：① 上线后**绝不复用已删除/废弃的旧 ID**，新内容一律顺延新 ID；② 有进行中/待领奖老玩家的表优先下架/禁用而非物理删行，物理删行前先与程序确认清理与统计口径；③ 严禁手改或删除 `*_mapping.json`；④ 想重置领奖资格必须新建业务 ID。
- **程序红线**：① 纯布尔状态优先 bit 存储且强制走导表器位序映射，状态归属业务表不绑 `Reward` 表；② 严禁手改 `*_mapping.json`；③ 查表必须判空容错、不拿原始 popcount 当有效总数、高位未知 bit 必须原样透传回写；④ 配置表支持热更，业务只存 `id` 用时现查，不缓存表行对象指针/引用。
